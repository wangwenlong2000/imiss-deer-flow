# 更接近用户使用方式的真实服务测试（2026-10-22）

最新开启业务思考的六组完整流程测试及新问题见 [2026-10-27 全过程报告](full-flow-thinking-service-check-20261027.md)，含多轮修改、零分母、空结果和错误恢复。

后续修复及同组完整流程复验见 [完整流程修复与复验](full-flow-fixes-20261022.md)。下文保留修改前的历史测试结论。

后续已完成业务执行、最终回答与附件下载测试，见 [完整业务流程实测](full-flow-service-check-20261022.md)。下文仍是业务执行前中断的识别测试，二者指标分开统计。

**主测试为 90 个新会话、120 个计划用户回合，严格通过 109/120（90.83%）；81/90 个会话全部回合通过。** 其中 116 个回合实际进入识别，另 4 个计划回合被前置的两次附件上传失败阻断。正常口语单轮为 40/40；主要问题集中在支持范围边界、结构化输出校验、澄清后路由和历史附件。

本批是根据用户使用方式自建、首次运行前冻结的合成场景，不是抽取的真实生产对话，也不能作为真实用户总体准确率。没有混入之前的 28 条原题、旧合成集或复测成绩。

## 怎么模拟用户

继续通过 **http://127.0.0.1:3328** 调用运行中的服务，模型始终为 **Qwen3.6-35B-A3B**。会话间并发 2，同一会话内按顺序提交用户消息，复用服务实际写入的 checkpoint，而不是为每轮手工指定“正确的上一轮场景”。

- 每个业务场景四种新说法，包含口语、省略、英文和相近专业词。
- 真正缺业务对象时，要求返回未知并提出澄清问题；不能靠“流量”“风险”等词猜领域。
- 测试否定、只翻译一句话、业务背景词和“最后给个表格”等输出要求。
- 测试两个或三个并行业务、去掉其中一个业务、切换话题、再回到之前的文件。
- 在同一会话中修改日期、对象和输出方式，检查结构化参数与路由，而不只检查场景标签。
- 真实调用上传接口，上传自建 CSV、PCAP、表格 JSON、Python、JPEG、TIFF。所有附件合计约 2.8 KB，只有合成数据；图片是中性占位图，仅用于上传及意图线索测试，不测试视觉定位、遥感计算等业务准确率。
- 澄清协议组使用生产 `ClarificationMiddleware._build_pending_action()` 构造的状态模板，并绑定前轮实际识别结果，测试选项数字、参数值和否定回复。这里的提问状态明确是测试夹具，不代表主模型已自动调用澄清工具。

所有调用在业务 `model` 节点前中断。因此，多轮测试覆盖的是**执行前规划、改需求与续接**；没有验证业务结果内容、文件计算结果或模型完成任务后的回答质量，也未向 OneCityAgent 平台发送消息。测试期间未修改后端源码、模型配置或场景标签；源码与用例哈希前后核验一致。

| 澄清选项/参数协议 | **7/8** | 未知场景选择“网络抓包”后仍保留空场景 |

按“已成功进入识别”条件统计为 109/116（93.97%），这只是条件指标，不能取代 109/120 的主结果。主统计与三轮失败复现、图片复测、历史附件对照均分开保存，不用最好一次替换首次失败。

24 项附加状态断言通过：9 项是否需要澄清、3 项时间/对象槽位、12 项选项/参数/取消回复与 pending 清除检查。场景正确、槽位正确、选项解析正确是不同指标；例如未知场景的选项虽解析正确，实际业务场景没有更新，仍计失败。

原始评测字段 `stale_skill_ids` 表示所选技能超出了“预期场景”的范围，不直接证明旧技能缓存未清。另行用技能注册表核对后，本批没有发现“识别场景已正确更新，但仍注入无关旧场景技能”的情况；四条该字段非空的主测试，源头均为场景识别本身错误。

## 耗时与调用次数

已进入识别的 116 回合：意图阶段观测均值 **1.55 秒**，请求均值 **3.52 秒**。这里请求计时从当前回合提交开始，到中断后状态读取结束，**不含新建会话、上传和业务执行**；与之前包含创建会话的测试耗时不可直接作提速比较。

四条被上传阻断的计划回合没有独立请求耗时，原始 summary 的全行平均把它们记为零，得到 3.41 秒；不要用这个值描述用户全链路平均耗时。失败上传也没有完整计时，上传总耗时不在当前平均数中。意图阶段是相邻中间件更新事件间隔，包含调度/传输观察开销，不是供应商纯推理时间。

流式唯一消息 ID 和模型元数据共观测到 **140 次逻辑模型调用**：

- 104 次结构化业务识别，包括两条失败任务的额外修复调用。
- 25 次对话轮次判断。
- 11 次合规边界复核。

所有模型名称均为 `qwen3.6-35b-a3b`。常规新任务仍是一轮结构化识别；多轮判断、校验修复和合规复核会增加调用，不能把全链路一律称为一次。消息流中的技能说明和规划 HumanMessage 已排除在模型调用计数外，也未将应用逻辑次数等同于供应商/SDK 物理重试次数。

100 条需要新展示规划、且已有有效规划字段的实际运行消息，经过移动端纯适配器 **100/100** 完整保留为 `task_planning` / `规划智能体`。这不覆盖那两条校验降级后丢失规划的运行，也不是向真实平台发送后的验收结果。

## 关键发现与复现

### 1. 模型已经选对场景，引用校验却把结果丢掉

`multi-3`：“一份是话单，一份是网络抓包，分别找共享终端和异常外联。”主测试和三次独立复现均失败。三次复现保存的原始模型 JSON 都包含 `phone_network` 和 `network_traffic`，但 evidence 使用了类似“一份是网络抓包...找异常外联”的省略号拼接。当前 `_parse()` 要求一个连续原文片段，修复一次后仍不满足，整份结果降级为规则判断，最终只剩电话网络。

`dialog-remove-domain` 第三轮的法律追问，首次和第三次复现失败，另两次复现通过。失败复现中，模型选了正确的 `policy_regulation`，但把上一轮与本轮的句子拼成 evidence，再次触发相同降级。

这两类不是简单的“模型不知道场景”，而是**正确语义结果被格式/引文校验否决**。建议保留来源校验，但支持分段真实引文或本地规范化，减少无效重问和整份结果丢失；不应为修正这些案例增加关键词硬筛选。

### 2. 未知场景澄清后，没有重新确定场景

`pending-missing-domain` 初始问“流量有没有异常”，随后在业务类型选项中回复“2”，对应“网络抓包”。选项对象解析、pending 清除均成功，但 `IntentRecognitionMiddleware` 直接恢复原来的空场景，未重新识别或更新业务场景。**首次和三次复现均失败**。

与之相对，已经知道是电话网络时，选择阈值策略、修改 `top_k=20` 等协议测试可以正常续接。需要区别“给已知业务补参数”和“通过澄清首次确定业务”，不能统一恢复旧意图。

### 3. 切题后回访最早附件，历史元数据没有进入识别输入

独立对照各用三轮：真实上传 capture.pcap → 检查抓包 → 换成审查合同 → “回到最早上传的那份文件，再看看它有没有问题”。两组第三轮均被判为 new_task，但：

- 自动使用历史附件的组，当前 `uploaded_files=[]`，错误识别为政策法规。
- 在当前消息里重新携带同一真实既有附件元数据的组，`uploaded_files` 含 capture.pcap，正确识别为网络流量。

这与上传中间件只把 `new_files` 写入状态、识别器剥离 `<uploaded_files>` 文本的实现相吻合。主测试里，四个成功上传会话的第二轮，`uploaded_files` 也全部为空；这四轮依靠前文任务仍识别正确，不能据此认为历史附件链路完整。应给意图识别提供受控的当前/历史附件清单与引用关系。

该组是追加的诊断对照，未计入主 120 回合。

### 4. 上传 Python 源码触发网关热重载，造成并发上传 502

当前 Docker 开发配置用 Uvicorn `--reload` 启动网关，没有排除 `.deer-flow` 用户运行目录。主测试真实上传 pipeline.py 后，WatchFiles 明确记录该上传文件触发 Reloading，随后网关进程退出并重新启动；当时 JPEG 和 TIFF 上传的 nginx 日志均为上游连接重置、返回 502。

按客户端时区，相关窗口为 **2026-10-22 17:41:34 至 17:41:54（Asia/Shanghai）**；原日志使用 UTC。容器本身没有重启，变化的是容器内开发服务器进程。

重载结束后，JPEG、TIFF 分别串行重测，各自两轮均通过，说明首次失败不能直接归因为图片格式不支持。没有再次上传 Python 来人为重触发服务中断；原始失败仍保留。应在开发服务器监视配置中排除运行数据/上传目录，避免真实用户分析代码时影响其他请求。

### 5. 范围外拒识与背景边界仍有短板

六类已经不在注册表中，但登记消防告警、洪涝告警、食品安全投诉仍分别被误分到政策法规或视频监控。只删除类别不能保证未知请求不被硬凑到相近类别。

一条“只翻译监控检测句子”的请求，首次误判代码分析，三次复现均正确返回空场景，说明这个边界存在偶发不稳定。不能通过删掉首次失败来声称问题消失。

## 修复优先级

1. 澄清后根据确认的业务重新确定场景；保留已知业务补参数的快速续接。
2. 避免连续引文格式校验误杀正确任务、丢场景和规划，优先在本地处理可修复格式。
3. 完整传递历史附件元数据与当前引用对象，防止切题后回访文件时沿用最近话题。
4. 从开发服务器热重载范围中排除用户上传/运行目录。
5. 补充范围外、纯翻译、背景与主目标的边界验证，保留未知路径。

本轮完成测试和定位，没有修改这些生产行为。以上结论来自运行服务的输出和明确的代码路径；尚未验证修复后的效果。

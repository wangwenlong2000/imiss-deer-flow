# OneCityAgent to DeerFlow compliance contract

## Trust boundary

OneCityAgent should populate `compliance_request` from its authenticated user,
authorization service, resource catalogue, and requested business operation.
DeerFlow derives the policy scene from those facts. `scene_hint` is advisory
only and never selects a policy cell.

The current DeerFlow development endpoint has no tenant IAM lookup of its own.
For production, direct public access to LangGraph must be blocked and the
Gateway must accept these facts only from an authenticated OneCity integration.

## Request

```json
{
  "messages": [
    {"type": "human", "content": "请分析该资源并生成内部报告。"}
  ],
  "compliance_request": {
    "request_id": "req-001",
    "actor": {
      "user_id": "user-001",
      "org_id": "org-001",
      "department_id": "dept-001",
      "roles": ["analyst"],
      "permissions": ["traffic.read"]
    },
    "operation": {
      "type": "analysis",
      "target_audience": "organization"
    },
    "resource": {
      "resource_id": "resource-001",
      "owner_user_id": "user-001",
      "owner_org_id": "org-001",
      "owner_department_id": "dept-001",
      "target_org_id": null,
      "classification": "internal",
      "is_anonymized": false
    },
    "scene_hint": "internal_org",
    "intent": {
      "intent_type": "analysis",
      "requested_operation": "analysis",
      "risk_level": "low",
      "is_high_risk": false
    }
  }
}
```

The recognized `intent_context.compliance_intent` generated by DeerFlow
overrides a caller-supplied `compliance_request.intent` before scene resolution.

### Actor

- `user_id`, `org_id`, and `department_id` identify the authenticated actor.
- `roles` are server-issued role names.
- `permissions` are server-issued entitlements. An empty or missing list does
  not prove access and resolves ordinary scenes to `_unknown`.

### Operation

`type` is one of `analysis`, `upload`, `export`, `share`,
`public_release`, or `research`. `target_audience` is one of `self`,
`department`, `organization`, `external_org`, `public`, or
`research_group`.

### Resource

The resource block carries the catalogue identifier and authoritative owner
user/org/department, optional target organisation, classification (`public`,
`internal`, `confidential`, or `restricted`), and anonymization status.
Unknown classification or ownership is a fallback condition.

### Untrusted fields

`scene_hint`, natural-language ownership claims, client-created role names, and
client-created permission strings are not authorization. DeerFlow ignores the
hint for resolution and compares actor/resource/operation facts. The upstream
Gateway/OneCity trust boundary must ensure the other fields were issued by
server-side systems.

## Resolution rules

Rules are evaluated in conservative priority order:

1. `public_release`: operation is public release, audience is public, or the
   canonical recognized intent is public release. This strict scene cannot be
   overwritten by a private hint.
2. `cross_org`: external audience, differing target org, differing owner org,
   or explicit external-share operation.
3. `_unknown`: required identity, ownership, classification, operation, or
   permissions are missing/invalid.
4. `research_anon`: research operation, research-group audience, server-issued
   research/statistics authority, and an already anonymized resource.
5. `self_use`: actor owns the resource, audience is self, permission is
   present, operation is not export/share/public release, and classification is
   not restricted.
6. `internal_org`: actor and owner org match, audience stays within department
   or organisation, permission is present, and the operation is internal.

Same-org cross-department access maps to `internal_org` and records
`cross_department_same_org`. Research without anonymization stays `_unknown`.
An illegal or conflicting hint never falls back to `self_use`.

## Resolver result

InputGate writes one authoritative `scene_context` into LangGraph state:

```json
{
  "scene": "internal_org",
  "confidence": 0.95,
  "source": "server_resolver",
  "reason_codes": ["organization_match", "permission_present"],
  "fallback": false,
  "permission_checked": true,
  "scene_hint": "internal_org",
  "request_id": "req-001"
}
```

ContextGate and OutputGate reuse this result. Policy receives only
`scene_context.scene`; it never reads `scene_hint`.

## Gate usage

- InputGate resolves the scene after IntentRecognition, passes the same
  structured request facts and resolution to Compliance Engine, and writes the
  result to state/SSE.
- ContextGate obtains `scene_context` from the tool-call state and passes it in
  the detection origin.
- OutputGate obtains the same context from model-call/graph state. Durable
  compliance metadata and retract events include the final scene.

If no contract exists, all gates retain the legacy `_unknown` behavior.

## Audit

An audited decision contains `scene_key`, `scenes`, `scene_resolution`, and
`request_context` in addition to detector findings, actions, basis, intent, and
audit reference. `request_context` contains actor identifiers/roles/permissions,
operation, resource ownership/classification, and the original hint. It must
not contain credentials or full source documents.

Example excerpt:

```json
{
  "audit_ref": "audit-...",
  "gate": "InputGate",
  "scene_key": "public_release",
  "scene_resolution": {
    "source": "server_resolver",
    "permission_checked": true,
    "fallback": false,
    "reason_codes": ["public_release_priority", "scene_hint_conflict"]
  },
  "actions": ["desensitize", "warn"],
  "hits": [{"violation_type": "struct_id"}]
}
```

## Compliance response and SSE

The state update that follows InputGate is:

```text
event: updates
data: {
  "ComplianceInputGateMiddleware.before_agent": {
    "scene_context": {
      "scene": "internal_org",
      "source": "server_resolver",
      "fallback": false
    }
  }
}
```

Output compliance metadata and the `compliance_retract` custom event use:

```json
{
  "gate": "OutputGate",
  "scene": "public_release",
  "violation_types": ["struct_id"],
  "actions": ["desensitize", "warn"],
  "basis": ["..."],
  "audit_ref": "audit-...",
  "retracted": true
}
```

Only bounded reason codes are exposed; internal chain-of-thought is not.

## Fallback examples

Missing actor:

```json
{
  "scene": "_unknown",
  "fallback": true,
  "permission_checked": false,
  "reason_codes": ["actor_identity_missing", "permissions_missing"]
}
```

Forged `self_use` for another user's resource:

```json
{
  "scene": "_unknown",
  "fallback": true,
  "permission_checked": true,
  "reason_codes": ["scene_not_proven", "scene_hint_unverified"]
}
```

An invalid enum, missing ownership, or missing operation is not a request error
that crashes the graph. It is an explicit conservative fallback and is visible
in state, policy selection, diagnostics, and audit when a finding exists.

## OneCityAgent handoff checklist

For every turn OneCityAgent must supply:

- a stable request ID;
- authenticated user/org/department IDs;
- server-issued roles and permissions relevant to the resource;
- operation and intended audience;
- authoritative resource owner user/org/department;
- target org for sharing;
- classification and current anonymization status.

The remaining customer integrations are the authoritative IAM permission
decision, resource catalogue ownership/classification lookup, department/org
hierarchy, external-organisation registry, and proof of anonymization. Until
those are wired, missing facts deliberately produce `_unknown`.

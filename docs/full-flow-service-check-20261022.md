## 测试范围和判定方式

首次请求前冻结了 [6 组/8 回合用例及预期数值](full-flow-service-eval-20261022/cases.json) 和 [合成附件哈希](full-flow-service-eval-20261022/frozen-inputs.json)。覆盖道路交通、网络流量、时空轨迹、程序片段、表格年鉴五类场景，包含同会话追问与真实澄清后的续接。

- 道路 CSV：两条道路共六条记录，独立计算分组总和、平均值、峰值与占比。
- 网络 flow CSV：六条合成流，独立核对流数、字节数、源 IP 排名与端口分布；不做实际网络探测。
- GPS CSV：九个点，A 应有两次恰好 20 分钟的停留，包含轨迹结束处的停留；B 只有 10 分钟，应为零次。
- Python 内联代码：生成真实 AST JSON，并实际执行验证返回值 16。没有上传 `.py` 文件触发开发服务器热重载。
- 虚构年鉴 CSV：同比均为 10%，两年 GDP 累计增幅为 21%。
- 模糊“流量异常”请求：让执行模型真正调用 `ask_clarification`，再提供完整道路数据，核对实际续接；没有注入伪造 pending 状态。

数值正确、路由正确、流程正常结束、文件可下载与解释可靠分别检查。核心数值人工对照冻结预期；CSV、AST、执行输出另有 [八项机器检查](full-flow-service-eval-20261022/analyze_results.py)，全部通过。没有用文本中出现正确关键词代替结果核验，也没有用一次通用工具算对结果来证明专用业务链路正确。

## 两轮配置为什么分开保存

首轮使用后端客户端默认的 `recursion_limit=100`，完成 8 回合，其中轨迹、代码任务因图步骤达到上限而失败。随后核实网页端实际配置在 `frontend/src/core/threads/hooks.ts` 中为 **1000**，移动端默认为 **300**；该上限计算的是整个图的步骤，中间件也占步骤，并非允许调用 LLM 的次数。

第二轮为全新六个会话，保持用例和预期不变，只把上限匹配网页端的 **1000**，作为下表主要观察对象。首轮结果完整保留，不把首轮失败替换为复测成功，也不把两轮合并成一个通过率。两轮各最多同时提交两个会话，开始第二轮时首轮尚有收尾请求，短暂全局提交并发可能达到四；这不是严格隔离的性能基准。

随后在前两轮全部结束后，又独立执行同一道路会话的两回合，检查无本次其他任务竞争时的耗时。模型、提示词、业务代码与测试预期均未调整。

## 发现的问题

### 1. 数据算对，最后解释仍会出错

道路统计表正确给出主路甲均速 30、支路乙 40，但结尾写“主路甲整体流量和速度均高于支路乙”，随后又说主路甲平均车速更低。数值表与解释直接矛盾。

年鉴回答的四个同比 10.00% 和累计 21.00% 正确，但结尾出现：

- “人口每一年增加 100 万人，GDP 每一年增加 200 亿元”：2024 年实际增加 110 万人、220 亿元。
- “复合年增长率约为 9.54%”：`sqrt(2420/2000)-1 = 10%`。

年鉴 CSV 保存了同比，但没有累计增幅 21% 一栏，且数值显示为 `10.0`，未满足统一保留两位小数的要求。首轮还出现“经济增长完全由人口扩张驱动”的因果解释，仅凭这张合成表不能得出该结论。

建议让最终陈述引用同一份结构化计算结果，对比较方向、同比/增量、复合增速等可计算结论做本地一致性检查，并检查请求的指标是否全部进入交付文件。无需为每次简单分析固定增加一轮 LLM 复核。

### 2. 场景错误会被通用表格工具掩盖

网络任务在两轮中都被识别为 `table_yearbook`。第二轮道路首轮为 `road_traffic`，追问却漂移为 `table_yearbook`；串行对照再次出现同样的追问漂移。

它们靠通用 `data-analysis` 或临时 Python 仍完成了统计，因而只看最终数字会漏掉问题。本测试验证了网络文件统计，却**没有验证网络专用 skill 的完整工作流**。如果后续任务依赖网络领域的协议处理、异常算法或证据规范，这种误路由可能造成更大影响。

业务对象应优先决定场景；CSV、汇总、排名是载体和操作，不应把明确的道路/网络业务改成表格年鉴。需要补充这种实际执行请求的语义边界测试，而不是恢复关键词硬筛选。

### 3. 真正澄清后，执行模型兜底掩盖了空路由

执行模型实际提出业务类型选项，生成 pending 状态；用户下一轮已经明确“道路交通流量”及完整规则和数据，pending 被清除，但恢复的场景仍为空。第二轮没有新的结构化场景识别调用，延续了上一轮未知意图。

最终执行模型从完整对话中理解并算对了结果，但场景过滤、规划展示和后续专用技能选择仍缺少正确状态。该问题与前次协议夹具测试一致，这次是由真实 `ask_clarification` 产生的完整交互再次验证。

### 4. 轨迹脚本的末段边界错误，使简单任务变成现场调试

原始 `extract_staypoints()` 只在离开半径后结算停留，轨迹在同一位置结束时没有结算末段。对同一冻结九点 CSV，本地直接调用原库也只得到一个停留，见 [独立脚本复核](full-flow-service-eval-20261022/trajectory-script-check.json)。

第二轮执行模型先运行技能，再检查只有一个结果，读取实现、尝试修复，最终在会话 `workspace` 中修改副本后得到正确两个停留。期间出现路径错误、错误函数参数等重试；一次修改已安装技能的尝试被只读文件系统拒绝，未改动仓库原技能。

最终结果正确，但代价是 **24 次工具请求、25 次业务模型调用**，加识别、标题和合规复核共 **28 次逻辑模型调用**；服务器实际执行约 67.59 秒，加排队约 32.85 秒，总计约 100.45 秒。应修复并回归技能本身的边界条件，避免每个用户请求都现场调试。

### 5. SkillResult 封装参数不兼容，造成无效重复

代码任务已经生成 AST、实际验证返回值 16，并成功展示文件；但调用 `invoke_skill(mode='wrap_output')` 时，模型反复把 `legacy_artifacts` 传成 JSON 字符串，而工具类型要求 `list[str]`。第二轮三次验证失败后，模型最终明确表示跳过输出封装；首轮在此处达到 100 步上限，没有最终回复。

这说明“文件已生成”“用户收到答案”“SkillResult 契约成功闭环”是三个不同事实。建议在工具边界对可安全解析的数组字符串进行规范化，或提供更简单明确的 schema；对相同错误限定重试并及时反馈，而不是一直重问。这里尚未实施修复。

### 6. 排队已经成为明显的总耗时来源

网页端配置组的八回合平均值：

| 计时范围 | 平均耗时 |
| --- | ---: |
| 包括本回合上传与下载检查，不含创建会话及用户思考 | **53.00 秒** |
| 流式业务请求，包括排队 | **47.41 秒** |
| 服务日志记录的排队 | **23.23 秒** |
| 服务日志记录的真正执行 | **24.17 秒** |
| 流中观测的意图中间件阶段 | **2.39 秒** |

排队与执行来自服务日志的 `run_wait_time_ms` / `run_exec_ms`，不靠相邻事件猜测。意图阶段是中间件事件间隔，含轮次判断、结构化识别及修复等，不能视作供应商纯推理时间。

这组共观测到 **86 次逻辑模型调用**：8 次结构化识别、2 次对话轮次判断、62 次业务执行、8 次合规复核、6 次标题生成。输入/输出 usage 共约 116 万 token，是这些调用累计的重复上下文量，并不是单个上下文长度；物理请求重试次数未另行核对。

单独执行同一道路会话时，首轮约 **22.84 秒**（排队 0.60 秒），追问约 **8.21 秒**（排队 0.94 秒）。并发组的同一追问是 **97.66 秒**，其中排队 **83.68 秒**。这证明本次慢请求很大一部分发生在执行前等待；还需结合实际 worker 并发与沙箱容量定位调度瓶颈，不能将等待时间全部归到意图识别，也不能把此对照当作已完成吞吐调优。

## 展示链路与本次边界

完整事件经过现有移动端纯适配函数回放：网页配置组 **7/7 条最终答复原文保留，1/1 次澄清保留，五个附件任务均有 files 展示段**。下载接口另已实际验证。

本次没有驱动浏览器检查页面渲染，没有向 OneCityAgent 平台推送消息，没有启用子智能体，也没有验证本地模型权重部署。实际推理仍使用当前配置的 DashScope Qwen。视频、街景、遥感、政策法规、电话网络未在这一批进行完整业务验收；小型合成文件的成功也不能推导出大数据或大附件的效果。

测试结束后核对，上一轮冻结的后端与配置文件哈希仍一致。本轮新增的是测试脚本、证据与报告，**没有修复上述生产行为**。优先建议处理技能脚本边界与工具参数契约，再处理路由/澄清状态和调度，并将最终陈述与结构化计算结果绑定。

# 项目架构整理与易安装改造计划

日期：2026-11-26。本文是改造方案与实施跟踪基线，依据当前仓库、此前环境与 Skill 盘点编写。首稿时尚未实现应用代码；截至本文件末尾的实施记录，已完成部分启动解耦、配置和部署原型，端到端安装验收仍未完成。

## 当前实施进度（2026-11-26）

已落地并有针对性测试覆盖的工作：OneCity API/Coordinator 应用工厂、显式 SQLite 注入与健康就绪检查；认证、历史和 DeerFlow 入口回归改为使用真实应用工厂；部署配置 Schema、秘密文件生成、配置渲染、Compose 原型、迁移入口及只读源码构建入口；Skill 运行清单生成器与只读核验器。OneCity API 在未认证访问时返回 401 JSON，不重定向到浏览器登录页。

当前验证记录：OneCity 定向回归在 Python 3.12 容器中 `90 passed`；部署配置/预检与 Gateway SQLite 迁移测试 `4 passed`；上述部署测试与 Skill 清单测试合计 `9 passed`；渲染出的 Compose 文件通过 `docker compose config --quiet`；Skill 清单覆盖 119 个 Skill、只读核验 `0 errors`。OneCity Python 3.13 镜像构建、完整 Compose 服务启动、外部服务连通、MySQL 空库安装、真实业务场景、备份恢复与第二台机器迁移尚未完成验收。因此当前 CLI 与 Compose 属于安装候选原型，不应当作已通过交付验收的生产安装包。

推荐方向：**保留现有技术栈和主业务链路，明确模块职责，统一配置和发布，再用 Docker Compose 提供可重复安装的版本包。** 第一轮优先解决新机器安装、初始化和维护问题；深度模块拆分逐步进行。

默认实施范围为 Linux x86_64 单机、OneCity 作为主入口、聊天模型使用已配置的兼容 API，业务场景按交付范围选择。ES、视觉模型和 NAS 可以本地部署或连接共享服务。完全离线另设实施项，不能仅靠打包现有容器实现。

## 1. 改造完成后应达到什么效果

| 目标 | 完成标准 |
| --- | --- |
| 架构能讲清楚 | 每个服务有唯一职责、入口、依赖、配置和数据归属；新维护人员能沿服务图找到代码 |
| 新机器可安装 | 应用节点只需系统基础工具、Docker Engine 和 Compose 插件；不手工安装应用 Python/Node 环境，不借用旧机器的容器或 venv 卷 |
| 配置集中 | 安装者维护一份部署配置及独立密钥文件，由工具生成各组件配置，不在多处重复填写同一个服务地址 |
| 发布可追溯 | 发布版本对应源码提交、镜像摘要、依赖锁、Skill/模型/规则摘要和数据结构兼容范围 |
| 按场景安装 | 选中的能力具备对应依赖与资产；未安装的能力不被展示为可用；轻量档有明确功能范围 |
| 能维护和恢复 | 有统一的检查、启停、日志、备份、恢复和升级入口，在第二台机器上完成恢复演练 |
| 对外可验收 | 环境检查、接口回归、真实场景和恢复演练分别留证，不以健康接口或模拟结果代替业务验收 |

第一轮不安排框架重写、数据库整体替换、Kubernetes 或分布式图执行。OneCity、DeerFlow 和视觉服务继续保留独立依赖环境。现有鉴权、会话归属、受理签名和三道合规闸属于改造的回归边界。

## 2. 当前主要问题与处理优先级

| 问题 | 当前依据 | 计划处理 |
| --- | --- | --- |
| 仓库统一了，完整安装流程还没有统一 | 当前生产 Compose 主要覆盖独立 DeerFlow 四服务；没有完整 OneCity Dockerfile/初装编排 | 新增完整发布与安装层，复用已有模块 |
| 主链路启动耦合旧服务 | Coordinator 的 `Scheduler` 在导入期创建旧 A2A 客户端；API 启动还会构造 Agent | 新增应用工厂和显式初始化，旧 A2A 独立装配 |
| 大文件承担过多职责 | Coordinator 约 2166 行；Gateway `routers/mobile.py` 约 2771 行，混合路由、身份、状态和事件处理 | 先固定行为，再逐块提取模块 |
| 依赖重建不确定 | OneCity Linux 清单有无条件 `pywin32`、缺 `flask-cors`；后端构建未冻结安装；沙箱存在已确认差异 | 分环境锁定、干净构建、定向业务验证 |
| 配置散落且依赖机器路径 | YAML、TOML、env、JSON 和脚本中存在重复地址及宿主绝对路径 | 部署配置生成器统一派生地址、路径和功能开关 |
| 初次安装需要人工补操作 | OneCity 自动建表调用被注释；缺完整迁移、角色种子和管理员流程 | 一次性迁移与初始化任务，支持重复执行 |
| 发布不能完整代表运行环境 | 专用部署依赖旧镜像 ID/venv 卷；OneCity 最新文件在容器可写层 | 从确认源码构建不可变发布镜像，配置与状态外置 |
| Skill 是否可用无法统一判断 | 已盘点 119 个 Skill、338 条依赖，但安装声明与执行环境还未统一 | 运行契约、依赖锁、资产清单和按能力自检 |
| 迁移容易遗漏数据 | MySQL、ES、Gateway SQLite、checkpoint、`.langgraph_api`、线程文件及 NAS 分散 | 建立数据归属清单和一致备份集合 |

现有 `backend/packages/harness/deerflow/` 与 `backend/app/` 已经体现框架层和应用层分离，不需要为整齐重新搬动全部目录。优先补安装层和启动边界，降低第一轮变更范围。

## 3. 推荐的目标运行架构

```mermaid
flowchart TB
    browser[浏览器] --> edge[Nginx：静态页面与统一入口]
    edge --> api[OneCity API：账号、工作区、业务会话]
    edge --> coordinator[Coordinator：流式适配、文件代理、IAM]
    api --> mysql[(MySQL)]
    coordinator --> mysql
    coordinator --> gateway[DeerFlow Gateway：鉴权、受理、任务与文件接口]
    gateway --> graph[LangGraph：任务执行与合规流程]
    gateway -. IAM校验 .-> coordinator
    graph -. IAM校验 .-> coordinator
    graph --> sandbox[按需创建的工具沙箱]
    graph --> chat[聊天模型 API]
    sandbox --> services[按场景：ES、Embedding、视觉模型等]
    sandbox --> assets[授权的数据集、模型与 NAS]
```

基础常驻服务是 Nginx、OneCity API、Coordinator、MySQL、Gateway、LangGraph，共六个；ES 本地部署时增加一个。工具沙箱按需创建，场景模型另计。API/Coordinator 复用同一个 OneCity 镜像，Gateway/LangGraph 复用同一个 DeerFlow 镜像。

| 组件 | 负责的事情 | 数据或边界 |
| --- | --- | --- |
| Nginx/静态前端 | 页面、同源 API/SSE 转发、上传限制 | 默认唯一公开入口；不公开内部 IAM 和原生图写接口 |
| OneCity API | 登录、令牌、角色、工作区、业务会话/历史 | MySQL 是账号与业务目录的权威来源 |
| Coordinator | OneCity 与 DeerFlow 协议适配、文件授权代理、IAM 回调 | 不重新判定任务是否成功，不另做一套合规结论 |
| Gateway | 权威 thread 映射、鉴权与签名受理、上传/产物、任务控制和业务事件转换 | 维护自身 SQLite 数据；不能信任前端传来的角色授权 |
| LangGraph/harness | 编排、工具/Skill、沙箱、checkpoint、合规闸 | 不导入 OneCity 账号实现，不依赖页面显示格式 |
| Skill | 对应场景的提示、脚本或组合流程 | 显式声明输入输出、执行环境、资产及服务要求 |
| StreetModel 等 | 独立模型推理接口 | CUDA/模型权重与应用、CPU 沙箱环境分开 |
| 旧 A2A/IM/独立网页 | 按范围保留的可选入口 | 不成为未选中功能的启动前提 |

第一版仍使用单 LangGraph 进程及已验证的本地持久化方式。当前 `langgraph dev --no-reload` 和进程内受理机制有单机边界；本轮交付不将其描述为高可用集群。今后需要多机扩容时，单独评估图服务部署方式、持久化、分布式配额和协议/许可要求。

## 5. 应用内部如何拆分

### 5.1 先解决 OneCity 的启动边界

建议新增以下模块，现有 `app.py`、`coordinator_sse_acting.py` 暂保留为兼容入口：

```text
apps/onecityagent/onecityagent/
  application/
    api.py                         create_api_app(settings, dependencies)
    coordinator.py                 create_coordinator_app(settings, dependencies)
  identity/
    service.py                     身份、工作区、角色、权限
    iam_routes.py                  仍挂载于 Coordinator 的内部 IAM 接口
  catalog/                         业务会话与资源归属访问
  integrations/deerflow/
    settings.py                    服务地址、超时、允许的产物来源
    client.py                      ensure/run/resume/status/cancel/upload
    models.py                      请求/响应结构
    stream.py                      SSE解析、中断与终态处理
    presentation.py                OneCity 页面消息适配
    artifacts.py                   产物URL验证与认证代理
    routes.py                      保持现有 /query/deerflow* 路径
  legacy/a2a/                      旧事件处置的显式初始化入口
```

实施顺序：

1. 先引入设置对象、应用工厂、可注入的数据库/客户端依赖，不触碰业务算法。
2. 将旧 Scheduler、MCP Agent 的构造移到明确选中的旧入口。核心模式启动不探测未启用 A2A 地址。
3. 先提取纯事件转换和 HTTP 客户端，再提取身份与文件代理；每次迁移保留旧路由和对应回归。
4. 旧模块最终只装配应用或转发兼容调用。API 与 Coordinator 第一轮仍分别运行，IAM URL 保持兼容。

目前 OneCity 部分测试通过截取源码或 AST 抽函数绕开完整导入。改造应补充正常 import、应用工厂和临时数据库测试，验证真实冷启动；旧测试可暂作行为对照。

### 5.2 再整理 Gateway 大型适配文件

将 `backend/app/gateway/routers/mobile.py` 逐步提取到应用层的 `mobile/` 模块，拆为请求模型、身份上下文、线程解析、run 控制、事件转换和路由装配。尽量让事件转换成为无网络和数据库副作用的纯函数。

先用现有 HTTP/SSE 样例固定实际生效行为，再处理重复定义；不能仅凭函数重名删除代码。保持 `harness` 不导入 `app.*` 的边界与既有测试。

### 5.3 用契约固定跨应用行为

在 `contracts/onecity-deerflow/v1/` 保存 JSON Schema、错误语义、事件序列和兼容样例，复用现有合规联调契约。Python 与 TypeScript 分别校验，不强行合并两套运行依赖。

必须覆盖：

- 登录/撤权、服务端身份解析、会话与 thread/run 绑定；前端字段不能赋予权限。
- submitted、pending、running、完成、失败、取消、断流和恢复；resume 只加入已存在 run。
- 401/403/404/409/429/503、`Retry-After` 及流内错误；不能统一包装成成功。
- 上传合规检查、上下文/输出合规、撤回、审计引用、产物来源和文件归属。

先冻结现有 URL 和语义。新增字段优先兼容旧消费者；协议升级或 GET/POST 调整单独安排，不夹在目录搬迁中。

## 6. 统一配置，同时区分发布配置、运行状态与秘密

### 6.1 唯一部署入口

建议安装者只填写 `config/deployment.yaml`，密钥通过独立文件引用。配置生成器负责输出 DeerFlow YAML、OneCity TOML/JSON、Compose 环境和 Nginx 配置。

部署配置包括：公开 URL、宿主根目录、启用场景、本地/外部数据库与 ES、聊天/向量/视觉端点、NAS 映射、追踪开关、容量参数和资产版本。配置 Schema 校验类型、必填条件、互斥模式和跨字段一致性。

例如，同一个 Gateway 地址派生 run、ensure、upload、file URL；IAM 地址与共享签名配置同时提供给 Gateway 和 Graph，安装者无需手工逐处对齐。

### 6.2 配置的优先级与写入边界

| 类型 | 存放方式 | 规则 |
| --- | --- | --- |
| 发布默认值 | 版本包内只读 | 随发布变更，有 Schema 版本 |
| 站点部署配置 | `config/deployment.yaml` | 安装者维护，渲染前校验 |
| 生成配置 | `generated/<generation>/` | 工具生成，不手工修改，校验后切换 |
| 秘密 | `secrets/` | 首次生成或导入；重复安装不轮换，日志/报告脱敏 |
| 运行管理状态 | `data/platform/` | Skill启停、MCP管理等，受管理接口控制并纳入备份 |

当前 Skill/MCP 管理接口会写 `extensions_config.json`，不能将所有配置简单改成只读。目标方案将可变状态与部署模板分离：静态配置加运行覆盖，Gateway 负责受控写入、文件锁和原子替换，Graph 只读共享并按明确机制刷新。需要原子替换的状态使用目录挂载，避免只挂单文件。

运行覆盖不得修改身份、签名、内部网络等部署级约束。配置生成与升级不能清空平台管理员的既有更改。此部分需要配置读取器和管理接口配套修改。

发布 Skill 代码默认只读；如交付范围包含动态安装 Skill，使用独立可写 overlay，由统一加载器处理名称冲突、授权和版本，不写回发布包。

### 6.3 消除机器相关配置

- 宿主路径与容器路径分字段：例如宿主 `/srv/citybrain/data/deerflow`，容器统一 `/data/deerflow`，由工具生成 AIO 的宿主映射。
- 容器内配置固定为 `/etc/citybrain/...`，不继承旧机器的绝对配置路径。
- Compose 内部使用服务 DNS；宿主服务和远程服务使用显式配置，移除对固定 `172.17.0.1` 的假设。
- 服务使用逻辑名：`chat_model`、`text_embedding`、`streetmodel`、`elasticsearch` 等，适配旧环境变量，逐步消除多套命名。
- LangSmith 等出网追踪使用显式开关，并校验最终生效值。当前运行配置与仓库 env 的差异应在 P0 映射时处理。

### 6.4 登录初始化

固定保存 Flask 会话秘密、RSA 私钥与受理签名密钥。已有环境迁移应导入原值；新环境生成新值。Gateway/Graph 共用受理签名，满足现有长度要求。

OneCity 当前前端公钥硬编码，应改为从同源运行配置或公钥接口获取，后端返回当前公钥标识。这样更换部署地址或新站点密钥无需专门重建前端；浏览器只能获得公钥和公开配置。调整时验证登录/注册兼容及公私钥匹配。

## 7. Docker 镜像、安装包与功能档

### 7.1 镜像策略

| 镜像 | 构建与运行策略 |
| --- | --- |
| OneCity | Python 3.13 独立 Linux 锁环境；API/Coordinator 复用镜像，分别以前台进程运行 |
| DeerFlow | Python 3.12 + uv workspace 冻结安装；Gateway/Graph 复用镜像，venv 固化在镜像中 |
| edge | Node 22 构建 OneCity 静态资源，运行阶段只保留 Nginx 和产物 |
| sandbox-compat | 第一版固定现有完整沙箱兼容环境并修复缺口；不用未限定的 latest |
| toolbox | 包含配置生成、迁移/诊断所需工具，支撑宿主轻量 CLI |
| StreetModel | 独立 CUDA 环境；可选 GPU 镜像或连接远程服务，保持模型与索引兼容 |

依赖锁应来自清理后的声明及干净构建验证，不把现网 `pip freeze` 当作唯一可复现来源。分别记录直接依赖、完整锁、系统工具、基础镜像 digest 与可验证构建材料。OneCity 的 pyproject/requirements 保留单一依赖来源，其余由工具导出。

前端用 `npm ci`/冻结锁构建；后端冻结 uv 锁；可选 Node/MCP 工具只有在功能选中时进入对应镜像。模型、图库、索引、编译缓存不进入每个应用镜像。OneCity与前端使用生产入口，所有服务关闭reload；首版LangGraph保留已验证的 `langgraph dev --no-reload` 单机运行时，其生产运行时迁移另行评估。

### 7.2 两种交付材料

```text
citybrain-release-<version>/
  citybrain                       统一命令入口
  manifest.json                   版本与兼容范围
  compose.yaml
  overlays/
  config/deployment.example.yaml
  templates/
  manifests/                      Skill、模型、规则、索引、许可证清单
  checks/
  docs/
  checksums.sha256
  images/                         无镜像仓库访问时附预构建镜像
```

在线交付从镜像仓库拉取固定 digest；无外网交付附同版本镜像归档和所选场景资产包。**离线安装材料不等于离线业务能力**：仍使用 DashScope、搜索或地图的配置需要对应网络。

秘密与业务数据独立交接，不放入通用 release 包。交付清单记录第三方包、模型和规则来源及许可材料。

### 7.3 功能档与运行档分开

| 部署功能档 | 适用情况 | 明确边界 |
| --- | --- | --- |
| 基础应用 | 先完成账号、问答、合规、上传、普通文档/表格与基础分析 | 仍需聊天模型；不宣称包含全部业务场景 |
| 共享服务场景档 | 应用在新机，ES/视觉/NAS等使用内网服务 | 新应用机可以无GPU；系统仍依赖共享服务 |
| 本机场景档 | 所选数据库、索引、模型和原始数据在目标机 | 涉及当前StreetModel时需要CUDA/GPU |
| 完全离线档 | 网络隔离，模型与服务均有本地替代 | 单列聊天推理、向量、地理/检索数据实施与验收 |

功能档决定安装哪些能力，沙箱运行档决定计算环境。第一轮保留一个兼容沙箱，后续增加基础档，再按实际收益拆出网络、遥感、视频或浏览器档。

## 8. Skill 标准化与沙箱管理

### 8.1 将已盘点的依赖转为运行声明

复用现有 `SKILL.md`、Router Card、`registry.json`、Input Envelope 与 SkillResult Schema。建议新增 `skills/skill_runtime.schema.json`，各 Skill 增加 `runtime.yaml`，只补运行信息：

- 执行类型：提示、脚本、服务、组合；对应动作的入口和参数 Schema。
- 运行档、解释器与最低版本、直接必需/按分支必需/可选依赖。
- 系统二进制、浏览器、规则、模型与数据资产引用及校验和。
- 服务逻辑名、凭据引用、网络要求、超时和重试条件。
- 输入输出位置、成功条件、错误码、允许的降级和代表性验证样例。

不重复人工维护场景名、路由描述等已有字段：确定各类元数据的唯一来源，由构建工具生成索引。现有 119 个 Skill、338 条依赖盘点作为迁移底稿，自动生成后人工复核。

### 8.2 第一轮先处理已知阻断项

| 项目 | 处理计划 |
| --- | --- |
| 街景 Python、ES 客户端声明与沙箱差异 | 选定经过验证的执行环境与客户端版本，验证ES9.3.3协议与检索行为 |
| 道路 RAG 固定版本不符 | 对照真实分支验证后形成可解的锁，不仅修改版本文本 |
| OpenGrep 文件有但无执行权限 | 发布阶段校验可执行位、版本和规则摘要，不能请求时对只读资产修复 |
| Playwright 包/匹配浏览器缺口 | 构建阶段一并准备，禁止验收时临时 npx 拉包掩盖缺项 |
| JS/C++解析、切分等条件依赖 | 根据启用语言与动作安装并做真实入口验证 |
| 旧 skills/public 路径、运行期自动安装 | 改为注册路径/资产引用和构建期依赖；缺项结构化报错 |
| OpenCV 包重叠 | 按真实导入结果与视频场景选择兼容实现，避免共享 cv2 被覆盖 |
| 遥感缺影像后生成示例数据 | 明确生产/演示模式，真实数据验收禁止静默生成示例替代结果 |

### 8.3 逐步建立执行器

现有 `invoke_skill` 主要提供 prepare/wrap_output，实际命令仍由智能体执行。第一轮先为稳定 CLI 增加适配，保留脚本内部逻辑；后续由统一执行器承接超时、退出码、产物登记和运行信息。

输入输出沿用现有 Schema。执行器校验真实退出状态、输出文件、归属及诊断，不能只根据传入的 `success` 字段认定成功。缺向量、切分回退、规则替代模型等应明确输出失败或 `partial_success` 及影响。新增执行模式、镜像摘要等字段时显式升级 Schema 并兼容旧消费者。

身份与线程归属来自受信执行上下文，不由 Skill 输入自由字段授权。纯提示 Skill 不要求伪造一个 Python 入口。

### 8.4 先统一沙箱网络，再考虑同会话多镜像

动态沙箱由宿主 Docker 创建，当前不会自动进入 Compose 网络。第一版应增加显式网络配置，让沙箱只接入所需服务网络；将控制接口访问、服务访问与宿主路径分别配置，并从真实沙箱验证。固定镜像必须预先加载，沿用请求时不自动拉镜像的行为。

当前按线程绑定一个全局镜像。后续若同一会话要使用多个运行档，需要新增调度：沙箱身份包含 thread、运行档、镜像摘要；运行中不能被另一档LRU回收；总量/用户配额统一计数；输出按调用隔离并登记给后续任务。此项独立实施，不作为首个可安装版本的前置条件。

## 9. 初次安装、数据迁移与恢复

### 9.1 新机安装流程

目标是安装者按以下流程操作。`citybrain` 薄入口及部分配置/生命周期命令已有原型；命令语法和目前可验证范围如下。`install` 尚未完成完整部署验收，`verify` 当前只做健康接口检查，不执行场景业务请求：

```bash
./citybrain --root /srv/citybrain init
# 编辑 /srv/citybrain/config/deployment.yaml，并准备独立秘密文件
./citybrain --root /srv/citybrain assets-import
./citybrain --root /srv/citybrain check
./citybrain --root /srv/citybrain config-render
./citybrain --root /srv/citybrain install
./citybrain --root /srv/citybrain verify --suite basic
./citybrain --root /srv/citybrain verify --suite scenes
```

`citybrain` 使用薄 shell 包装调用版本匹配的 toolbox 容器；无外网包可先加载 toolbox，再执行配置生成和安装。应用节点无需额外安装项目 venv 或 Node。Docker/Compose 及 GPU 相关系统前提由部署文档说明并由检查器校验。

| 命令 | 负责的步骤 |
| --- | --- |
| `init` | 建立目录/配置模板；仅首次创建秘密，保留已有值 |
| `check` | 校验配置、镜像/资产、目录权限、端口、磁盘及选中依赖，生成脱敏报告 |
| `install --mode fresh` | 校验空环境、加载固定镜像、启动本地数据服务、迁移/种子、启动应用、执行基础检查 |
| `start/status/logs/stop` | 管理同一Compose项目；start不隐式升级数据库或安装依赖 |
| `verify --suite ...` | 分基础、接口、真实场景验证；真实模型调用和数据范围单独标记 |
| `backup/restore` | 创建/校验一致备份集合，优先恢复到新目录 |
| `upgrade plan/apply`、`rollback plan/apply` | 展示兼容范围、数据迁移与回退方式，再执行确定的计划 |
| `export-evidence` | 导出版本、环境、场景验证及恢复记录 |

安装分步记录安装ID和进度，可重试且幂等。失败保留诊断和已有数据，不自动清空数据库。fresh 模式遇到本安装ID已创建的数据库时，校验进度与迁移记录后继续，或返回已经安装；遇到外部已有、来源不明或记录不匹配的数据库时停止并给出迁移路径，不能覆盖现有安装。

检查分为只读预检和显式运行验证。预检不修改索引、不触发任务；深度验证从Gateway、Graph和真实沙箱分别检查实际调用链，明确哪些会调用模型或产生测试数据。

### 9.2 数据初始化要成为正式组件

1. **OneCity/MySQL**：新增带版本与 checksum 的迁移记录；初始化表、普通角色等必需种子，单独创建管理员。重复执行不重置密码或重复创建角色。
2. **已有 MySQL**：先对照实际 schema 建立受支持的 baseline；不能只因表存在就标记迁移完成。DDL可能隐式提交，失败采用可恢复分步方案，不承诺一次事务回滚全部结构。
3. **Gateway SQLite**：自管表建立版本迁移，保留组织/用户/会话唯一约束和既有 legacy 导入语义。无归属旧记录不自动认领。
4. **LangGraph/checkpoint**：由固定的上游版本管理，独立记录兼容范围，不与Gateway自管表混用迁移号。
5. **ES**：新装创建所需mapping/模板；迁移优先同版9.3.3快照恢复并验证字段、维度和模型revision，不默认重建现有向量。

应用启动仅检查结构兼容性，不把迁移放在首个业务请求中。迁移作为一次性任务在应用接流量前运行，并有互斥控制。

### 9.3 运行目录与数据归属

```text
/srv/citybrain/
  releases/<version>/             不可变发布
  current                         当前发布引用
  config/deployment.yaml
  secrets/
  generated/<generation>/
  assets/<asset-version>/         Skill、模型、规则、数据集清单及资产
  data/
    platform/                     可变管理配置、动态Skill overlay
    deerflow/                     gateway.sqlite3、checkpoint、线程与审计
    langgraph/                    .langgraph_api 运行状态
    mysql/                        或统一管理的命名卷
    elasticsearch/                或统一管理的命名卷
  logs/
  backups/<backup-id>/
```

NAS可保留独立挂载，清单记录实际路径与授权。秘密目录采用受限权限；用户线程目录按运行 UID/GID 和用途设置权限，避免用全目录放宽权限解决安装问题。

### 9.4 备份、迁移与回退

一致备份集合至少包括：MySQL逻辑备份、ES快照及必要配置、Gateway SQLite、checkpoint、`.langgraph_api`、线程上传/产物、审计、站点配置与秘密、资产版本和NAS映射。模型和大数据可通过受校验的资产包引用，不要求每次重复打包。

跨多个状态源迁移应先停收新任务、排空并停止写入，再生成同一 backup set。SQLite使用正确备份方式；不热拷贝MySQL/ES数据目录。仅 `docker save` 不包括卷或容器可写层，不能作为完整迁移方案。

恢复默认在新目录/新Compose项目验证后切换。版本回退区分镜像/配置回退与数据恢复；涉及破坏性DDL、checkpoint或向量变化时，需要兼容迁移或恢复备份，不能只切换 `current`。

### 9.5 启动与健康检查

数据服务 → 一次性迁移/种子 → 应用进程 → 对外入口 → 全链路验证。场景服务按选择启用。

存活检查验证进程；就绪检查验证自身配置和必要存储；深度检查另行验证模型与整条链路。避免 OneCity 等待DeerFlow、DeerFlow又等待OneCity IAM的循环就绪依赖。Nginx保持SSE不缓冲及所需长任务设置，内部IAM路径不从公开入口转发。

## 10. 分阶段实施安排

估算以熟悉现有项目的人员、复用现有回归、基础版使用现有聊天API为前提；单位为人日，不是服务器运行时间，也不是已验证工期。完全离线替代、新GPU模型引入、大规模数据搬运等待时间不在此估算内。

| 阶段 | 工作与主要交付物 | 依赖 | 估算 | 退出条件 |
| --- | --- | --- | ---: | --- |
| P0 固定基线与契约 | 服务/数据图、交付能力矩阵、版本manifest规范、当前配置映射、关键HTTP/SSE样例 | 无 | 2–3 | 交付来源明确，代码/镜像/资产可追溯；选中能力的依赖有归属 |
| P1 最小入口与依赖 | OneCity应用工厂、旧A2A初始化隔离、Linux可解依赖锁、前台生产入口 | P0 | 4–6 | API/Coordinator正常import冷启动，不访问未启用A2A；现有鉴权与历史回归通过 |
| P2 配置与镜像编排 | 部署Schema/渲染器、秘密引用、前端运行配置、OneCity/DeerFlow/edge/toolbox镜像、完整Compose | P0；OneCity构建需P1 | 5–7 | 干净构建并从镜像启动；不借旧venv卷；不同部署根目录可用；动态沙箱网络可达 |
| P3 首装与管理CLI | MySQL/Gateway迁移、角色与管理员初始化、check/install/start/status/logs、安装文档 | P1、P2 | 4–6 | 干净Linux/空库安装，两次执行幂等；登录、问答、上传下载、重启持久化闭环 |
| P4 Skill与场景交付 | 119个Skill运行分类/声明、已知缺口修复、选中场景资产包、模型与索引版本校验 | P0，可并行准备；运行验证需P2/P3 | 6–10 | 所有交付Skill声明可校验；选中场景真实样例通过，缺依赖与降级明确留证 |
| P5 内部模块整理 | OneCity client/identity/stream/artifacts分层；Gateway mobile模块拆分；测试逐步改为factory正常导入 | P1及已冻结契约，可与P4并行 | 5–8 | 路由与行为兼容，跨账号/终态/合规/断流/取消回归通过，harness边界保持 |
| P6 迁移与交付验收 | backup/restore、升级兼容矩阵与回退、第二台机器演练、证据导出、运维手册 | P3、P4；涉及P5的新版本再回归 | 4–6 | 第二台干净机器安装与恢复通过，账号/数据/文件/场景完整，升级回退有实证 |

总体约 **30–46人日**。建议至少一位应用负责人、一位构建/部署负责人，配合测试支持；可按约4–6周安排首轮，再在P0后根据合同场景与实际数据库差异修订。

关键依赖关系：`P0 → P1 → P2 → P3 → P6`；P4清单准备可提早，真实场景在新编排中验证；P5在契约固定后与P4并行。P3完成可先提供安装候选版，P4/P6通过后才形成对应场景的验收发布。

建议拆成独立PR：基线/契约、OneCity冷启动、配置生成、镜像与Compose、初始化CLI、Skill依赖修复、OneCity分层、Gateway分层、迁移恢复。业务算法、框架替换与大规模目录重命名单独立项。

## 11. 验收门槛与测试复用

| 验收层 | 必测项 | 证据 |
| --- | --- | --- |
| 构建与安装 | 干净构建、锁安装、镜像/资产校验；仅Docker前提初装；更换根目录；重复安装；中断后重试 | 构建日志、manifest、check报告、安装记录 |
| 身份与协议 | 两账号登录/撤权、跨组织/账号拒绝、同名文件隔离、SSE状态、429、resume/cancel、合规与审计 | 接口断言与脱敏事件序列 |
| 真实业务 | 真实聊天模型、各选中场景的数据/检索/模型执行、数值和产物正确、证据可下载 | 固定输入、模型名/模式、实际运行档、输出及耗时 |
| 状态与恢复 | 重启后历史与文件可读、队列/任务终态正确、一致备份恢复、升级失败回退 | 第二台机器演练记录及数据核对 |

复用现有 `make onecity-test`、`make onecity-test-client`、`make onecity-verify` 以及 `scripts/verify_onecity_*` 和后端IAM/合规/并发/沙箱测试。增加的测试重点验证新边界、完整应用导入、空库安装和恢复流程，不为目录移动机械复制一套测试。

安装验证与真实业务验收分别运行。真实模型输出不要求逐字相同：冻结模型配置、样本、数值/结构和证据判据。明确记录模型调用失败、降级和未覆盖项；旧开发回归分数不当成新的独立验收精度。

容量由一个配置源派生并实测。此前盘点现网为3执行/10运行加等待/每用户2，新部署脚本默认3/6/2，二者不得混写成同一基线。新机器冻结硬件、样本规模和并发后再给出时延/吞吐门槛。

镜像大小、空闲/执行内存、冷启动时间、安装人工步骤及总耗时在P0记录，P3/P6复测。优化以测量为依据，首轮不承诺未经验证的镜像缩减比例或最低硬件规格。

## 13. 建议的实施起点与后续范围

先完成P0并确定一个安装候选版本，再做P1–P3：**启动解耦、依赖固定、统一配置、完整Compose、数据库初始化和安装CLI**。这部分最直接减少部署难度，也为后续架构拆分提供稳定验证环境。

随后并行处理P4场景交付与P5模块整理，最后在P6完成第二台机器验证。多运行档沙箱、本地聊天模型/完全离线、分布式执行或更换存储作为后续独立计划，按实际需求评估。

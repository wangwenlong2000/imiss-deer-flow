# 跨机器迁移与 Docker 部署指南

日期：2026-11-26。依据当前仓库、现网部署盘点及 [Skill 依赖盘点](Skill依赖版本盘点_20261126.md) 编写。本次仅整理步骤，没有停止、备份或变更现网服务，也没有在目标机器执行部署。

## 1. 推荐方案与部署范围

可以使用 **Docker Compose 单机部署**。推荐先采用“应用、数据库、工具执行迁到新机，大模型继续使用现有 API”的方案。若街景模型、ES 或 NAS 继续共享旧机服务，必须确保新机真正可达；这属于分布式部署，旧机不能同时退役。

“全部迁移”需要区分三种范围：

| 范围 | 新机器承担的内容 | 外部依赖 / 资源 |
| --- | --- | --- |
| 应用迁移、重型服务共享 | OneCity、DeerFlow、工具沙箱；数据库按需要本地或共享 | 使用云模型 API，可共享 ES、视觉模型和 NAS；新应用节点可以不配 GPU |
| 独立应用环境、云模型保留（推荐的完整交付起点） | 应用、MySQL、ES、数据、所需向量/视觉服务、全部合同场景资产 | 聊天模型和搜索/地图仍联网；本地 StreetModel 当前要求 CUDA，因此需要 GPU |
| 完全离线 | 上述全部，另需本地聊天模型、向量、地理数据和检索服务 | 当前项目没有可直接启动的本地 Qwen 聊天部署；公网实时搜索、天气、路况等需替代方案，不能承诺离线完全等价 |

Docker 可以隔离 Python/Node 版本、减少重复构建和简化启停。模型权重、ES 索引、原始图库、运行内存和推理算力仍需单独准备。

## 2. 推荐的轻量部署结构

```text
浏览器
  → Nginx（OneCity 静态页面、统一 HTTP/HTTPS 入口）
      → onecity-api（登录、账号、会话管理）→ MySQL
      → onecity-coordinator（SSE、上传/下载、IAM bridge）
          → gateway → langgraph → 按需创建 AIO sandbox
                            ├─ 大模型 API
                            ├─ Elasticsearch
                            ├─ Embedding / StreetModel（按场景）
                            └─ 数据集 / NAS
```

保留 OneCity 主入口时，基础常驻服务为 **Nginx、OneCity API、Coordinator、MySQL、Gateway、LangGraph，共 6 个**；ES 本地运行则为 7 个。模型服务按合同场景另计，工具沙箱动态创建。Gateway/LangGraph 复用一个后端镜像，OneCity API/Coordinator 复用另一个镜像，运行进程仍分别管理。

独立 DeerFlow 的 Next.js 网页如不在交付范围，可以不部署。OneCity 的旧 A2A 事件处置入口和额外智能体属于另一条功能链；仅使用 `/query/deerflow` 主链路时，不要求常驻所有旧 A2A 智能体。若合同包括旧事件处置、知识库或工具管理，必须补齐相关服务。

轻量化建议：

1. 使用前端生产构建，关闭开发 reload；前端编译所需 Node 工具只保留在构建阶段。
2. 使用 Linux slim 基础镜像分别构建 Python 3.12 的 DeerFlow 与 Python 3.13 的 OneCity，保留各自环境。
3. 从一个图执行任务和低并发开始，按真实任务测量后再增加。沙箱数量、内存需求和图任务数一起规划，不把进程数量直接当作吞吐能力。
4. 暂不需要的 SkillRouter、IM、额外前端和场景服务不启动；保留其功能时则不能删除相应依赖。
5. 模型、数据与索引使用持久化目录/卷，不打入每个应用镜像；动态沙箱共用只读镜像层，各自仍占用运行内存和可写空间。
6. 按场景拆分沙箱镜像可进一步瘦身，但当前 provider 使用统一镜像，自动按 Skill 选择镜像还需要实现，不能直接删包后宣称所有 Skill 等价。

资源可先按以下预算做方案讨论，**不是已经验证的最低要求**：联网 API、单个小型业务任务的应用节点可从 8 vCPU、16–32 GiB RAM、200 GiB SSD 起做试部署，业务数据与备份空间另加。本地 ES、并发、遥感和视频处理需要更高内存；本地视觉与离线聊天模型的 GPU/显存应按实际模型和并发测量，不能从当前 80GB 显存服务器推导最低规格。

本次只读镜像盘点：旧 OneCity 基础镜像约 **20.85 GiB**，AIO 镜像约 **3.91 GiB**，说明重新构建 OneCity 应用镜像有瘦身空间；这些是镜像内容大小，不是进程内存，也不能简单相加作为物理磁盘占用。旧 OneCity 镜像不包含容器运行后写入的最新应用文件，不能直接当作完整发布件。

## 3. 当前仓库可以复用什么，尚需补什么

| 组件 | 当前可复用 | 跨机交付仍需完成 |
| --- | --- | --- |
| DeerFlow | `backend/Dockerfile`、`frontend/Dockerfile`、生产 Compose | 修正配置路径、补合规/数据挂载，固定版本；现有图运行时仍是 `langgraph dev` |
| OneCity | 完整源码、`scripts/onecity.sh` 前台入口、Node 22 构建 | 仓库暂无 OneCity Dockerfile；需构建 Linux 运行镜像、静态资源和容器间代理 |
| MySQL | 现网 8.0.39 | 初装/种子数据或现网逻辑备份，恢复验证 |
| Elasticsearch | 现网 9.3.3 | 全场景索引盘点、同版本快照/恢复、认证和访问配置 |
| 工具沙箱 | Dockerfile、现有镜像、Skill 依赖清单 | 修复已发现的依赖差异和执行权限，交接本地镜像和主机路径映射 |
| StreetModel | 独立安装/启动脚本与固定依赖声明 | 权重、上游实现、CUDA 环境；如果容器化还需 GPU 镜像与服务定义 |
| 专用部署包脚本 | `prepare/start/status` 可参考 | 依赖已有源容器、venv 卷与旧主机绝对路径，不是空白机器安装器 |
| 完整迁移编排 | 各模块部署说明 | 尚无覆盖上述全部模块的跨机 Compose、首次初始化及恢复编排 |

因此，当前根目录 `make up` **只覆盖 DeerFlow 四服务，不等于整套项目部署完成**。本指南给出需要完成的交付流程，不将尚未编写的完整 Compose 文件描述为已可执行。

## 4. 步骤一：固定交付版本和资产清单

先确定交付本仓库 HEAD、11-12 专用发布快照，还是经过修复的新版本。不要将三者的代码、依赖卷和配置混合拼装。记录 Git/文件摘要、镜像摘要、模型与规则版本、配置摘要及备份时间。

交付包分成以下部分，并分别建立校验和：

| 部分 | 需要包含 |
| --- | --- |
| 应用发布 | 后端、OneCity、静态前端、119 个 Skill、检测器实现、启动编排 |
| 私有配置 | OneCity TOML/JSON、运行环境、数据库和 API 凭据、IAM 签名配置、登录密钥 |
| 镜像 | 应用 release、AIO、Nginx、MySQL、ES，以及选定的模型服务镜像 |
| 模型与工具 | 合规分类权重、街景/YOLO/文本向量权重、OpenGrep 与规则、Playwright 包和浏览器资产 |
| 业务数据 | ES 全部合同场景索引、NAS 图库/视频、数据集、OneCity 数据库 |
| 运行状态 | DeerFlow 数据根、checkpoint、图本地状态、上传和产物、审计；按是否迁移历史决定 |

注意：本仓库里 `models/`、`datasets/` 的内容不能代表现网全部资产。只读盘点得到现网街景模型目录约 **9.1GB**、街景数据目录约 **14GB**，NAS 原图库另计；ES 还包含手机网络、遥感、证据、规则及多数据处理等索引。不能只导出最初检查过的六个索引。

## 5. 步骤二：完成镜像与初装准备

优先在构建机生成经过验证的 release 镜像，再分发到目标机器；目标机器无需安装所有 Python/Node 开发工具。若目标无外网，镜像、权重、浏览器和安装材料须提前准备。

DeerFlow、沙箱现有构建入口可复用，例如从仓库根目录执行以下命令；它们**只构建对应模块，不代表完整迁移已就绪**：

```bash
docker build -f backend/Dockerfile -t citybrain/deerflow:release-20261126 .
docker build -f docker/sandbox/Dockerfile -t citybrain/sandbox:release-20261126 .
# 仅交付独立 DeerFlow 网页时需要：
docker build --target prod -f frontend/Dockerfile -t citybrain/deerflow-web:release-20261126 .
```

正式发布应冻结依赖安装并固定基础镜像摘要。当前 backend Dockerfile 使用 `uv sync`，沙箱大量依赖没有精确固定；不能把“新构建成功”当作“与现网依赖完全一致”。

OneCity Linux 镜像准备时，需先解决本轮确认的问题：

- `requirements.txt` 中 `pywin32==310` 没有 Windows 平台条件，不能原样在 Linux 安装；应限制为 Windows 或从 Linux 依赖集合排除。
- `app.py` 导入 `flask_cors`，但当前清单未列 `flask-cors`；需补齐经过验证的依赖。
- 前端使用 Node 22、`npm ci` 和 `npm run build`；运行时 Nginx 托管 `dist/`，无需启动 Umi 开发服务器。
- 前端安装/构建时仍需提供 `ONECITY_BACKEND_URL` 和 `ONECITY_COORDINATOR_URL`，否则 Umi 配置加载会失败。
- API 和 Coordinator 用前台进程入口，分别为 `python app.py` 和 `python onecityagent/service/a2a_service/coordinator_sse_acting.py`，工作目录设为应用根目录。现有 `scripts/onecity.sh api/coordinator` 已采用前台 `exec`，可参考。
- 不直接把旧 `start.sh` 当最小容器入口：它启动全量后台进程，而且部分配置前置要求与当前同源文件代理方式不一致。

还需处理 [Skill 盘点](Skill依赖版本盘点_20261126.md) 中街景 Python/ES 客户端、道路 RAG 版本、代码解析/切分依赖、Playwright 和 OpenGrep 执行位，再对交付场景验证。不要将已知缺口原样打包后称为完整验收版本。

## 6. 步骤三：准备目标主机和目录

优先选 Linux x86_64，并确认已安装 Docker Engine 和 Compose 插件。当前镜像为 linux/amd64；ARM 机器需要另行构建和验证。若本地运行 StreetModel，先准备 NVIDIA 驱动；GPU 容器另需 NVIDIA Container Toolkit。现有宿主 Python 服务也可保留独立虚拟环境运行，不要求立即容器化。

建议统一目录：

```text
/srv/citybrain/
  release/                   只读发布源码/静态资源/编排
  config/                    私有配置，不混入镜像
  skills/                    技能与工具资产
  models/                    权重
  datasets/                  共享数据集
  data/
    deerflow/                SQLite、线程文件、审计
    langgraph-runtime/       .langgraph_api
    mysql/                   或使用命名卷
    elasticsearch/           或使用命名卷
  logs/
  backups/
```

NAS 可继续挂到 `/mnt/nas/streetview_meta`，或使用新目录并同步修改全部路径映射。私有配置目录设为 0700、密钥文件设为 0600；线程文件按沙箱配置的 UID/GID 准备可写权限，避免对整个数据根目录递归放宽权限。

## 7. 步骤四：备份并迁移数据

如果是全新账号/全新数据部署，按初始化流程建立数据库和资源。如果要保留现有账号、会话、上传及产物，应先安排任务排空，阻止新增写入，做最终一致性备份后再迁移。

| 对象 | 推荐迁移方式 |
| --- | --- |
| MySQL | 使用与现网兼容的逻辑备份/恢复，包含表结构、数据及所需角色/业务配置；目标先用 8.0.39 降低变量 |
| ES | 优先 9.3.3 同版 snapshot/restore；保留 mapping、settings、aliases、模板以及对应认证/访问配置 |
| DeerFlow | 备份完整 `/data/deerflow`，包括 `gateway.sqlite3`、`checkpoints.db`、线程文件和审计；在停止写入后备份，或使用正确的 SQLite 备份流程 |
| 原生运行状态 | 独立迁移 `.langgraph_api`；仅备份 checkpoint 不能覆盖全部运行和恢复状态 |
| NAS、模型和规则 | 校验后复制或重新挂载；保留原文件名、权限和与索引对应的标识 |
| OneCity | 备份实际运行的配置、登录密钥、静态产物和必要发布文件；现网入口容器没有宿主卷，最新配置在容器文件层 |

不能边写边直接复制 MySQL/ES 数据目录，也不能只复制运行中 SQLite 的主文件而忽略 WAL 状态。ES 快照需单独准备可读的 repository；认证密钥和未包含在所选快照中的配置仍要独立交接。不要将 ES 8 或 OpenSearch 当作当前 ES 9.3.3 的等价替换。

`docker save` 保存镜像，不包含命名卷、bind mount 数据或运行容器可写层中的后续修改。因此，单独保存旧 OneCity 镜像会漏掉最新发布；保存后端镜像也会漏掉现网独立 venv 卷。

## 8. 步骤五：重写服务地址、挂载和身份配置

内部地址使用 Compose 服务名；外部地址按目标网络填写。以下是**目标配置示例**，需由完整迁移编排落地，不是当前文件的默认配置：

| 配置 | 示例 / 要点 |
| --- | --- |
| MySQL | `mysql:3306`；数据库名和凭据与恢复结果一致 |
| ES | `http://elasticsearch:9200`；沙箱若不在 Compose 网络，需使用其真实可达地址 |
| OneCity → DeerFlow | `DEERFLOW_API_URL=http://gateway:3330/api/deerflow/mobile/run` |
| 确保会话 / 上传 / 内部文件 | 对应的 `DEERFLOW_THREAD_ENSURE_URL`、`DEERFLOW_THREAD_UPLOAD_URL`、`DEERFLOW_FILE_INTERNAL_BASE` 全部切向同一 Gateway |
| 浏览器下载 | 走 OneCity 同源认证代理；不要要求浏览器访问 `gateway:3330` 私网 DNS；`DEERFLOW_PUBLIC_BASE_URL` 按实际代理逻辑设置 |
| Gateway → 图 | `LANGGRAPH_URL`、`MOBILE_ADAPTER_LANGGRAPH_URL` 指向 `http://langgraph:3329` |
| 两后端 → IAM | `MOBILE_IAM_PROVIDER=app.gateway.onecity_iam:OneCityIAMProvider`，`MOBILE_IAM_ENDPOINT=http://onecity-coordinator:7010/internal/deerflow/iam`，`MOBILE_IAM_REQUIRED=true` |
| 签名受理 | Gateway/LangGraph 共用同一随机 `DEER_FLOW_ADMISSION_SIGNING_KEY`（至少 32 字节），`DEER_FLOW_REQUIRE_SIGNED_ADMISSION=true`；不发送到浏览器 |
| 容器内数据 | `DEER_FLOW_HOME=/data/deerflow` |
| 宿主数据源 | `DEER_FLOW_HOST_BASE_DIR=/srv/citybrain/data/deerflow`，与上面目录实际挂载对应 |
| 宿主 Skill | `DEER_FLOW_HOST_SKILLS_PATH=/srv/citybrain/skills`；其他 `mounts[].host_path` 也必须是宿主真实路径 |
| 应用配置 | 明确设置容器内 `DEER_FLOW_CONFIG_PATH`、`DEER_FLOW_EXTENSIONS_CONFIG_PATH`，并挂到相同路径；不要沿用旧主机绝对路径 |
| 沙箱访问宿主 | Linux 添加 `host.docker.internal:host-gateway`，设置 `DEER_FLOW_SANDBOX_HOST`；数据/模型服务地址另行验证 |
| 追踪 | 明确设置 `LANGSMITH_TRACING`；若关闭需显式为 false，不能只改旧 `LANGCHAIN_TRACING_V2` 而遗留更高优先级 true |

Nginx 和 OneCity 如果拆成容器，原模板中的 `127.0.0.1` 上游要改成对应服务名。Coordinator 实际监听端口由 `[a2a].router` 配置决定；不要只改环境变量而保留旧 TOML URL。

若用 `envsubst` 渲染 Nginx 模板，应只替换列出的部署变量，保留 `$uri`、`$host`、`$proxy_add_x_forwarded_for` 等 Nginx 变量。

动态 AIO 沙箱由宿主 Docker 另行创建，当前实现不会自动加入 Compose 私网。因此 `elasticsearch`、`streetmodel` 这类服务名不能假定在沙箱内可解析；应提供沙箱可达的受控宿主入口，或在实现中增加网络接入。当前 `172.17.0.1` 地址也不能假定在新机成立。

## 9. 步骤六：初始化数据库、登录与外部资源

迁移已有数据库时，核对表结构、用户/工作区关系和普通角色，再启动应用。全新初始化时，现有 `create_tables()` 可作为建表入口，但 `app.py` 中自动建表调用被注释，且没有完整的初装种子/迁移脚本；必须补齐普通角色等基础数据。自助注册默认要求有效的 `code=common` 普通角色，仅创建空表还不能直接注册。

在目标数据库已创建、私有配置已填写且应用依赖已安装的前提下，可从 OneCity 应用目录运行已有建表函数：

```bash
.venv/bin/python -c 'from onecityagent.models.db_models import create_tables; create_tables()'
```

此命令不创建数据库本身、不初始化普通角色，也不负责已有库的结构升级；恢复现网数据库应走单独的恢复流程。

登录 RSA 公私钥要成对迁移：后端使用配置指向的 `private.pem`，前端当前有固定公钥。若新生成后端私钥，需要同时替换前端公钥并重新构建。`SECRET_KEY` 固定保存，不能每次容器重启都随机变化。现网实际配置还包括容器内 `.onecity-runtime.env` 和 `config/`，不能只寻找仓库 `.env`。

外部资源按功能确认：

- **聊天模型**：DashScope/Qwen 账户、额度、模型名和兼容 API；若改成本地模型，需要另建推理服务并验证思考、视觉、工具调用及合规复核接口。
- **StreetModel**：原服务只监听旧机 localhost/bridge，新机不能直接访问；共享时需要新的内网入口，本地时搬权重、上游实现和 CUDA 环境。当前服务无 CUDA 返回 503。
- **BGE / RAGFlow**：本轮原地址分别连接拒绝/根路径超时；需要恢复或新建，不能把不可达地址当作已交付服务。
- **SkillRouter**：当前关闭，维持现状无需先部署两套模型；启用时再准备服务与索引。
- **地理/搜索/MCP**：地图、Photon、百度搜索、Jina、高德、微信等按合同功能交接账户和出网条件；实时公网能力在离线环境需另做替代。

## 10. 步骤七：按依赖顺序启动并核验

完整迁移 Compose 准备并经过校验后，按以下顺序启动；不要求用 Kubernetes：

1. 导入镜像；先确认本地存在 AIO 配置引用的镜像标签。当前 AIO 使用 `--pull never`，不会在请求时自动拉取。
2. 启动并恢复 MySQL、ES，挂载数据和权重；检查所需索引与原图可以对应。
3. 启动选定的 Embedding/StreetModel 等场景服务并验证沙箱网络路径。
4. 启动 OneCity API/Coordinator 与 IAM bridge。最小方案不启旧 A2A，但其配置中的旧黑洞地址可能在导入期触发请求，应清理地址并验证冷启动。
5. 启动 Gateway/LangGraph，验证 IAM、签名密钥、合规启动和持久化路径。
6. 启动对外 Nginx，保留 SSE 不缓冲、长任务超时和上传限制；公开入口拒绝 `/internal/`，内部 API 和数据库不直接公开。

镜像交付可使用标准 Docker 命令，例如：

```bash
# 构建机：只包含已确认的镜像；数据库/模型镜像按交付清单另行加入
docker save -o citybrain-images.tar citybrain/deerflow:release-20261126 citybrain/sandbox:release-20261126

# 目标机：先核对交付文件校验和，再加载
docker load -i citybrain-images.tar
docker image ls
```

实际的 `docker compose up -d` 必须针对交付包中补齐的完整 Compose 执行；不要把现有 `docker/docker-compose.yaml` 的成功启动理解为 OneCity、数据和全部场景已恢复。

## 11. 步骤八：验收、切流与回退

新环境先用合成小样本验证，不直接覆盖旧服务。至少包括：

1. 两个普通账号登录、会话持久化、同名文件上传/下载、跨账号拒绝、退出后失效。
2. 真实模型问答、计算与产物交付；各合同场景至少一条真实数据链路，尤其是需要向量、原图、视频或遥感的路径。
3. 合规正常/违规/异常上传、审计关联；依赖缺失、模型错误和超时不会被误报为成功。
4. 执行、排队、429、取消与断线恢复。小机器先低并发，容量以实测为准；当前现网 3/10/2 不是任何目标机都适用的容量保证。
5. 重启后账号、历史、线程映射、上传、产物及审计仍可用；数据库和文件恢复演练通过。
6. 全链路确认没有意外访问旧主机服务；若保留共享服务，明确其地址、责任和可用性范围。

切流前再次排空旧机任务并同步最终数据，切流后只保留一处权威写入。保留旧机和备份用于回退；两边分别产生新写入后，不能简单切回而假设数据自然合并。

## 12. 交付就绪判断

具备以下内容后，才能把迁移交付描述为“另一台机器可按步骤部署”：完整 Compose、已验证的 Linux 应用镜像、配置模板、初装/数据恢复流程、模型/规则/图库清单、所需服务网络路径、冻结版本与校验和、验收结果和回退说明。

当前已完成环境与依赖盘点及本指南；完整跨机 Compose、OneCity Linux 镜像和初装自动化仍需工程整理。此阶段建议先固定推荐的联网 API 方案及目标机器配置，再据此形成实际交付包，避免将完全离线和应用迁移混为同一工作量。

## 新问题与定位证据

### 1. 思考模式与计算门禁的强制工具选择冲突

道路第三轮明确要求“解释就行，不要调用工具”。对话判断为 `task_followup`，复用旧意图时仍带 `requires_computation=true`。模型解释后，计算门禁因本轮没有执行工具而插入一次纠错，并设置 `tool_choice` 为指定 bash 的对象。

当前 DashScope 接口拒绝了这组参数，真实错误为：

> The tool_choice parameter does not support being set to required or object in thinking mode

这是此前加入的计算门禁与思考模式之间的兼容缺陷；原有单元测试没有覆盖当前真实接口的限制。同时，多轮复用没有根据“只解释”更新计算标志，是触发它的上游原因。

证据：[失败状态与工具轨迹](full-flow-thinking-eval-20261027/thinking-on/road-evolution-turn-3.result.json)、[白名单错误记录](full-flow-thinking-eval-20261027/provider-errors.json)。优先修正本轮任务约束的更新，并使纠错步骤遵守当前模型服务的工具选择限制，避免发送被拒绝的组合。

### 2. CSV对NA过严，对精度改写又漏检

零分母的增长率按用户要求写 `NA` 是合理结果。现有检查把非空增长率单元格全部当作定点数字，因 `NA` 不满足“两位小数”而拒绝。年鉴首轮12次 `present_files` 全部失败，循环检测结束运行，最终答案只剩强制停止信息和合规提示。

第二轮模型正确改出了三位小数，但“把增长率的小数精度改成三位”没有被格式解析器识别。成功交付的校验对象完全没有 `decimal_places`，因此这次文件精度正确依赖模型执行，工具未证明它。

本地隔离复现进一步确认：数字和空基期通过、显式 `NA` 被拒绝；对这句三位小数改写，即使合成文件实际只有 `10.0`，不声明精度也会被接受。证据：[本地复现与对照](full-flow-thinking-eval-20261027/csv-local-reproductions.json)。应区分有效数值与明确约定的缺失标记，并将精度要求作为当前任务状态更新的一部分。

### 3. 正确识别被引文格式校验整体否决，降级丢任务

双目标首轮的两次模型原始输出都包含 `table_yearbook` 和 `program_snippet`，且 `requires_computation=true`。失败发生在代码引文：模型把原文中的换行与缩进压成了空格，两次引文校验均失败。

随后整体退回确定性分类，结果只剩 `program_snippet`，计算标志变成 false，规划与执行只围绕代码展开。实际执行得到函数返回值2，但最后只说明AST生成，未交付GDP两个同比，也未报告返回值。

证据：[两次原始输出、逐项引文检查和降级状态](full-flow-thinking-eval-20261027/quote-fallback-reproduction.json)。只做空白归一后的诊断检查，两段引文都能对应输入；这项诊断没有修改生产校验。应改善代码引文的表达与格式校验，并避免一次字段校验失败后静默丢掉独立任务和计算要求。

### 4. 错误被同时适配为失败和已完成

离线回放真实SSE后，移动端适配器为道路失败回合同时输出：

- `system / failed`：发生 `BadRequestError`。
- `final / completed`：内容为“正在通过工具核验计算结果。”。

这是占位消息被当作终结回答的问题。下游若只读取最后一段，可能把失败当成完成。证据：[对外适配离线回放](full-flow-thinking-eval-20261027/mobile-replay.json)。没有向外部平台发送这些结果。应让错误/中断状态优先于占位消息，单独界定有效最终回答。

### 5. 文件生成、可下载和展示登记没有闭合

代码除零回合生成了 `ast.json`，工作区下载接口返回成功，异常解释也正确；但没有调用 `present_files`，状态 `artifacts=[]`。修正代码的下一回合则正常登记了Python与新AST。

这说明单看文件存在或模型声称“已导出”，不能判断附件已进入展示协议。证据：[该回合实际状态](full-flow-thinking-eval-20261027/thinking-on/code-error-recovery-turn-1.result.json)。需要在结束前检查用户要求的交付文件是否已登记。

### 6. 多文件交付要求每次覆盖全部指标，造成重试和空列补丁

轨迹第二轮需要“用户次数汇总”和“空停留明细”两份CSV。工具在每次交付时要求声明全部指标；只交付次数汇总时，仍要求开始/结束时间和时长，最终模型在次数汇总里补上空时间列才通过。

本地对照中，两份文件与各自检查一次批量提交能够通过；分别交付时，即使状态已有明细附件，也不累计已覆盖指标。应明确指标属于哪份文件及批量交付约定。该回合最终数据正确，但四次交付失败属于额外成本。

## 总体观测与边界

- 主测15轮中，14轮图正常结束、1轮SSE接口错误；正常结束中包含1轮强制停止，不能报告为14轮任务成功。
- 严格场景预期为13/15已执行回合一致。按全部16个计划回合保留阻断，则为13/16；这不是全过程完成率，也不代表真实用户总体准确率。
- 本轮任务流均值24.79秒，排队均值0.87秒、实际执行均值23.90秒。意图中间件观测均值3.10秒，包含多轮判断和结构化修复。用例与之前不同，并混有失败回合，不作思考开关的速度或准确率对照结论。
- 观测到130次逻辑模型调用、9467个reasoning tokens。最慢的年鉴首轮64.50秒、22次调用；识别之后的工具交付重试仍是重要耗时来源。
- 主测28次文件下载核验（含历史文件重复下载）均HTTP成功、字节数与SHA-256一致；正确文件不代表业务答案或展示登记完整。
- 同一失败会话的原第四轮在[独立恢复补测](full-flow-thinking-eval-20261027/recovery-road/road-evolution-recovery-turn-4.result.json)中耗时21.11秒、8次调用，得到 `average_flow([100,300])=200.0` 并登记AST，说明该400未永久破坏会话。
- 合成汇总表仍出现 `domain`、`re_identify` 等合规提示，需要单独标注复核；本轮不把这些提示直接计为已证实的合规模块误判。文字中仍有未验证的定性推断，也未据此宣称全文零错误。
